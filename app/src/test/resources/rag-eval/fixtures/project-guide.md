# 订单中台项目经验复盘（测评专用）

本文档为 RAG 测评人工编写的虚构项目复盘，人物、公司与数据均为虚构。

## 项目背景与架构

订单中台项目服务于虚构的电商业务，日均订单量 300 万，大促峰值日订单量 2000 万。整体架构是 Spring Boot 微服务，按领域拆分为订单服务、库存服务、营销服务、支付服务四个核心服务，服务间通信用 gRPC 同步调用加 Redis Stream 异步解耦的组合。

订单库采用分库分表方案，按用户 ID 哈希分成 16 个库、64 张表，单表数据量控制在 500 万行以内。分片键选择用户 ID 而不是订单 ID，原因是 90% 以上的查询都以用户维度发起。订单 ID 使用雪花算法生成，保证全局唯一且趋势递增。

## 缓存设计

订单查询的热点数据放入 Redis 缓存，缓存 key 按用户 ID 分桶，过期时间设置为 30 分钟加 0 到 5 分钟随机偏移，避免同一时刻批量过期造成缓存雪崩。缓存更新策略采用先更新数据库再删除缓存的旁路缓存模式，删除失败时投递到重试队列补偿。

大促前通过离线预热脚本把 TOP 商家的订单索引提前加载进缓存，预热命中率目标 95%。实际压测结果显示缓存命中率达到 96.4%，数据库 QPS 峰值被控制在 8000 以内。

## 异步消息与失败处理

订单履约链路使用 Redis Stream 作为消息通道，Stream 按业务领域拆分为 order-stream、inventory-stream、delivery-stream 三条。消费者组名称按服务实例编号区分，消费位点由消费者组自动维护。

Redis Stream 消费失败的处理规则是：消费失败最多重试 3 次，重试间隔按 1 秒、5 秒、30 秒阶梯递增，3 次仍失败的消息进入死信流 dead-letter-stream 人工介入。消息堆积告警阈值设置为 1 万条，触发告警后值班同学先扩容消费者再排查慢消费根因。

幂等性保障依靠订单号加业务类型的唯一索引，消费者处理前先查幂等表，处理成功后写入处理记录。补偿任务每小时扫描一次超时未完成的订单状态机节点，对卡住的节点按状态机定义重放。

## 性能与容量

下单接口的容量目标是 P99 延迟不超过 200 毫秒。全链路压测在预发环境进行，压测流量通过影子表隔离，压测数据的表名带 shadow_ 前缀。第三轮压测的下单接口 P99 延迟是 80 毫秒，P50 延迟是 23 毫秒，单实例吞吐 1200 QPS。

容量规划按大促峰值的 1.5 倍冗余申请资源。订单服务平时 8 个实例，大促扩容到 24 个实例。数据库连接池使用 HikariCP，最大连接数按实例数乘以单实例池大小控制在数据库总连接预算之内，连接池最大 20，最小空闲 5。

## 线上故障复盘

最严重的一次故障是营销服务批量发放优惠券导致 Redis 主从切换，切换期间缓存请求超时拖垮了订单查询链路。恢复时长 12 分钟。改进措施有三条：优惠券发放增加平滑限速、查询链路增加缓存降级开关、Redis 集群升级为三主三从并把只读请求路由到从节点。

另一次典型故障是慢 SQL 导致数据库连接池耗尽，根因是运营后台一个未走索引的订单导出查询。改进措施是运营后台查询强制走只读从库，并给导出接口加独立线程池与限流，导出任务白天限流到 10 QPS。

## 监控与发布

核心链路的监控覆盖黄金四指标：延迟、流量、错误率、饱和度。下单成功率告警阈值 99.9%，接口 P99 延迟告警阈值 200 毫秒。日志采集使用 Vector 收集到 Loki，链路追踪使用 OpenTelemetry 上报，采样率在线上设为 10%。

发布流程是：CI 通过后先发布预发环境做冒烟，生产环境按金丝雀批次发布，第一批 1 个实例观察 10 分钟，无异常后按 25%、50%、100% 三批推进。每批之间保留 5 分钟观察窗口，任何批次成功率下降超过 0.1% 立即自动回滚。

## 团队协作与成长

项目组采用两周一个迭代的节奏，需求评审后用 ADR 记录关键架构决策，每个 ADR 包含背景、候选方案、取舍理由三部分。线上事故复盘遵循无责文化，复盘产出必须包含时间线、根因、改进项三类信息，改进项指定到人并跟踪到关闭。
