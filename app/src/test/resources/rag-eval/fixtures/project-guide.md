# 订单中台项目经验复盘（测评专用）

本文档为 RAG 测评人工编写的虚构项目复盘文集，人物、公司与数据均为虚构。GMV 等经营数据由数据团队统一口径统计，不在本文档范围内。

## 项目背景与架构

订单中台项目服务于虚构的电商业务，日均订单量 300 万，大促峰值日订单量 2000 万。整体架构是 Spring Boot 微服务，按领域拆分为订单服务、库存服务、营销服务、支付服务四个核心服务，服务间通信用 gRPC 同步调用加 Redis Stream 异步解耦的组合。

订单库采用分库分表方案，按用户 ID 哈希分成 16 个库、64 张表，单表数据量控制在 500 万行以内。分片键选择用户 ID 而不是订单 ID，原因是 90% 以上的查询都以用户维度发起。订单 ID 使用雪花算法生成，保证全局唯一且趋势递增。

服务拆分的边界原则：订单服务只负责订单状态机与订单数据，库存、营销、支付各自独立库与团队。跨服务查询通过 CQRS 的读模型聚合，订单列表页的冗余字段由异步消息同步，读服务允许秒级延迟。

接口设计规范：对外 REST 对内 gRPC；分页必须传游标而不是页码；所有写接口必须幂等；超时预算按调用链路逐层递减，网关总预算 800 毫秒，订单服务内部预算 500 毫秒，下游依赖最多 300 毫秒。

## 数据模型与状态机

订单主表按买家维度分片，订单明细、支付流水跟主表同库保证本地事务。订单状态机包含待支付、已支付、履约中、已发货、已完成、已取消、退款中共七个状态，状态流转由状态机引擎驱动，非法流转直接拒绝并记录审计。

状态机的实现要点：流转规则配置化而不是 if else 硬编码；每次流转写入流转流水表；补偿任务按流水表扫描卡住的中间态；状态变更发布领域事件供下游订阅。

历史数据归档：已完成超过一年的订单迁移到归档库，归档库按年分表，用户查询一年前订单时服务自动路由到归档库，归档迁移用双写加校验的方式保证不丢。

## 缓存设计

订单查询的热点数据放入 Redis 缓存，缓存 key 按用户 ID 分桶，过期时间设置为 30 分钟加 0 到 5 分钟随机偏移，避免同一时刻批量过期造成缓存雪崩。缓存更新策略采用先更新数据库再删除缓存的旁路缓存模式，删除失败时投递到重试队列补偿。

缓存一致性对账：每晚抽样对比缓存与数据库的订单状态，不一致率告警阈值百万分之一，发现后强制失效并复盘根因。上线变更期的 key 结构变化通过版本号前缀隔离，新版本写新 key，观察一周后下线旧 key。

大促前通过离线预热脚本把 TOP 商家的订单索引提前加载进缓存，预热命中率目标 95%，实际达成情况见后文大促保障总结章节。

本地缓存层：对极热 key 再加 Caffeine 本地缓存，容量一万条，过期时间 5 秒，刷新采用异步 reload 防止击穿。多实例本地缓存一致性不追求强一致，5 秒窗口内的脏读由业务容忍。

## 异步消息与削峰

订单履约链路使用 Redis Stream 作为消息通道，Stream 按业务领域拆分为 order-stream、inventory-stream、delivery-stream 三条。消费者组名称按服务实例编号区分，消费位点由消费者组自动维护。

削峰设计：下单洪峰先进 Stream，履约消费者按固定速率消费，速率由配置中心动态调整。秒杀场景在入口层再加队列缓冲，超出容量的请求快速失败返回稍后重试，不让用户线程堆积。

消息可靠性：生产端用 RocketMQ 事务消息或本地消息表兜底（Redis Stream 场景用本地消息表），消费端幂等表去重。消息体只携带稳定 ID，消费者以数据库实体为事实来源，这个原则在团队内强制执行。

延迟消息：订单超时未支付自动关闭用延迟消息实现，关单消息延迟 30 分钟，关单前再查一次订单状态防止误关已支付订单。

## 消息失败处理细则

消费失败的基础规则很克制：消费失败最多重试 3 次，避免无限重试拖垮下游。超过次数的消息不再原地重试，进入人工处理流程。

重试的节奏与兜底在故障演练中反复调优：重试间隔按 1 秒、5 秒、30 秒阶梯递增，3 次仍失败的消息进入死信流 dead-letter-stream 人工介入。消息堆积告警阈值设置为 1 万条，触发告警后值班同学先扩容消费者再排查慢消费根因。

死信处理平台：死信流的消息进入管理后台，支持按错误类型分组、批量重放、单条诊断与错误备注。每周复盘死信 top 错误类型，属于代码缺陷的进迭代修复，属于数据问题的写修复脚本。

幂等性保障依靠订单号加业务类型的唯一索引，消费者处理前先查幂等表，处理成功后写入处理记录。补偿任务每小时扫描一次超时未完成的订单状态机节点，对卡住的节点按状态机定义重放。

## 性能与容量

下单接口的容量目标是 P99 延迟不超过 200 毫秒。全链路压测在预发环境进行，压测流量通过影子表隔离，压测数据的表名带 shadow_ 前缀。第三轮压测的下单接口 P99 延迟是 80 毫秒，P50 延迟是 23 毫秒，单实例吞吐 1200 QPS。

容量规划按大促峰值的 1.5 倍冗余申请资源。订单服务平时 8 个实例，大促扩容到 24 个实例。数据库连接池使用 HikariCP，最大连接数按实例数乘以单实例池大小控制在数据库总连接预算之内，连接池最大 20，最小空闲 5。

压测方法论：基准压测摸单接口上限，容量压测按流量模型混合场景，稳定性压测以峰值 1.5 倍持续两小时观察内存曲线与连接回收。压测报告必须包含瓶颈定位与下一轮优化项，没有结论的压测不算完成。

## 线上故障复盘

最严重的一次故障是营销服务批量发放优惠券导致 Redis 主从切换，切换期间缓存请求超时拖垮了订单查询链路。恢复时长 12 分钟。改进措施有三条：优惠券发放增加平滑限速、查询链路增加缓存降级开关、Redis 集群升级为三主三从并把只读请求路由到从节点。

另一次典型故障是慢 SQL 导致数据库连接池耗尽，根因是运营后台一个未走索引的订单导出查询。改进措施是运营后台查询强制走只读从库，并给导出接口加独立线程池与限流，限流阈值见后文导出治理章节。

第三次值得记录的故障是发布引入的：一次重构把本地缓存刷新改成了同步刷新，发布后高峰期线程池排队导致超时。教训是缓存刷新这类非关键路径必须异步化，评审清单里加了同步阻塞检查项。

故障复盘制度：无责文化，复盘产出必须包含时间线、根因、改进项三类信息，改进项指定到人并跟踪到关闭。S1 故障 48 小时内出复盘，改进项完成率进团队季度考核。

## 库存与营销子系统

库存扣减方案演进：一代用数据库行锁扣减，热点行锁竞争严重；二代拆分库存分桶，把一个 SKU 的库存拆成十六个子桶分别扣减，取桶时随机路由，桶内不足时借桶；三代热点 SKU 进 Redis 用 Lua 脚本原子扣减，异步落库对账。三代方案上线后秒杀场景库存接口 P99 从 400 毫秒降到 35 毫秒。

超卖的防线有三层：Redis 扣减脚本判断与扣减原子；数据库层 stock 大于零的条件更新兜底；对账任务每五分钟核对 Redis 与数据库库存差值，超过阈值告警并冻结交易。

优惠券系统：券模板与用户领券分离，领券记录按用户分片。券核销走消息异步核销，核销失败进入重试。防刷维度包括设备指纹、同 IP 频次、新账号限制与风控名单。

价格计算引擎：营销价、会员价、拼单价的多规则叠加用责任链计算，规则优先级配置化。价格计算的单元测试覆盖三百多个用例，任何规则变更必须先过用例库再发布。

## 支付与对账

支付网关对接了三个支付渠道，渠道适配层统一抽象为下单、查询、退款、回调四个动作。回调验签失败与金额不一致直接拒绝并告警。渠道接口都有独立的超时与重试配置，重试只对查询类接口开放。

对账体系：每日 T 加一拉取渠道对账单与本地支付流水逐笔核对，差异单自动挂起进入人工处理。长款短款分别统计，连续三天有差异自动升级。对账任务失败要有补跑机制，报表口径以对账结果为准。

退款设计：退款先冻结再执行，退款成功后解冻并回写订单状态。退款重试带退避，渠道返回处理中时不能当作失败重试，要区分终态与中间态。

## 消息推送平台复盘（虚构项目二）

推送平台日均推送 8000 万条，峰值每小时 3000 万。链路是业务方调推送 API 写入推送任务，平台按用户标签圈人，圈人结果写入发送队列，发送端按渠道分发。

核心技术决策一：圈人与发送解耦。圈人是重 IO 的批处理，用 Spark 离线加 presto 实时双链路；发送是高并发网络 IO，用 Netty 自研发送网关。两层之间用任务表衔接，互不拖累。

核心技术决策二：到达率与速率控制的平衡。厂商通道有每秒配额，发送网关按通道配额令牌桶限速，超配额的请求排队而不是丢弃。到达率从 92% 提升到 97.3% 的关键是失败原因细分：无效 token 清理、静默期尊重、厂商选择按历史到达率动态加权。

核心技术决策三：海量数据的存储分层。发送明细只保留七天，之后归档到对象存储，统计聚合按小时与天两级预聚合，运营看板只查聚合表。存储成本因此下降 60%。

推送平台的教训：初期用一张大表存发送明细，写入高峰把从库拖垮，改造为分表加归档后才稳定。所有大表设计必须先想清楚写入峰值、保留周期与归档路径。

## 实时数据看板复盘（虚构项目三）

实时看板项目为大促作战室提供秒级指标：下单量、支付成功率、履约积压、接口错误率。链路是业务埋点进 Kafka，Flink 消费做窗口聚合，结果写 Redis 与 ClickHouse，看板前端长轮询刷新。

技术要点一：指标口径统一。每个指标有口径文档与负责人，Flink 作业与离线数仓同口径校验，差异超 1% 阻断发布。口径不一致的实时看板比没有看板更危险。

技术要点二：Flink 作业稳定性。checkpoint 设为 30 秒，端到端 exactly once 依赖两阶段提交 sink；反压监控接到告警；作业升级用 savepoint 平滑迁移。大促期间作业变更冻结，只允许参数调优。

技术要点三：看板可用性降级。ClickHouse 故障时看板自动降级到 Redis 最近一小时缓存数据并标注数据时间，作战室不能出现白屏。

## 网关重构复盘（虚构项目四）

老网关是自研 servlet 网关，大促时线程模型扛不住长连接，重构选型对比了 Spring Cloud Gateway 与 Nginx 加 Lua 两个方案，最终选前者：团队 Java 栈统一、过滤器生态可复用、灰度按用户标签路由原生支持。

重构的迁移策略：新旧网关并行，按服务维度逐个切流，切流比例 1%、10%、50%、100%，每个阶段观察错误率与延迟对比。三个月完成全部服务迁移，期间出现一次证书配置错误导致回滚，回滚预案提前演练过，十分钟恢复。

网关的核心能力沉淀：鉴权过滤器统一 JWT 校验，限流过滤器对接 Redis 令牌桶，灰度过滤器按用户哈希与标签分流，Trace 过滤器注入与透传 traceId。网关自身的配置变更走配置中心热更新，不需要重启。

## 测试与质量策略

测试分层：单元测试覆盖领域逻辑，集成测试覆盖仓库与服务边界，契约测试锁定跨服务接口，端到端测试只覆盖下单支付主链路的十几个场景。测试环境的数据库用 docker compose 起独立实例，集成测试之间按业务域隔离数据，互不污染。

回归防线：CI 流水线跑单元与集成测试，合入主干前必须有增量覆盖率报告；每日 nightly 跑端到端与性能冒烟；发布前在预发跑冒烟集合。测试失败优先修，不允许跳过测试合代码。

混沌工程：大促前做故障演练，预案库里包含依赖服务超时、Redis 主从切换、数据库主库重启、可用区断网四类场景。演练发现的最大问题是缓存降级开关的粒度太粗，从全局细化到按业务域。

## 安全与合规

接口安全：管理后台全部走双因子登录，敏感操作二次确认。对外 API 签名包含时间戳与 nonce 防重放，密钥按应用隔离并支持轮换。数据安全：手机号与地址字段存储加密展示脱敏，导出需要审批并水印。日志脱敏检查进 CI，正则扫描明文手机号与身份证。

权限模型：RBAC 为骨架，资源维度到店铺与品牌，运营只能看授权范围内的数据。权限变更审计保留两年。第三方合作走开放平台，回调接口必须幂等且验签。

## 团队协作与工程文化

迭代节奏：两周一个迭代，需求评审后用 ADR 记录关键架构决策，每个 ADR 包含背景、候选方案、取舍理由三部分。代码评审 24 小时内响应，评审重点是设计正确性与边界，格式问题交给工具。

值班制度：每周轮值，值班手册包含常见故障的 SOP 与联系人矩阵。大促值班双人制，一人操作一人复核。值班交接必须过一遍未关闭的告警。

新人培养：入职第一周跑通本地环境并提交第一个 PR，第一个月负责一个小需求全流程，导师制度配对评审。技术分享双周一次，分享内容沉淀到团队知识库。

## 成本优化专项

成本优化的第一性原理：先计量再优化。每月出成本报表按服务拆分计算、存储、网络三块。优化案例一：日志采样率从全量降到 10%，日志存储成本降 70%，采样策略保留 ERROR 全量。优化案例二：低负载服务夜间缩容到最小实例，白天弹性扩容，计算成本降 25%。优化案例三：对象存储生命周期规则把三十天前的冷数据转低频存储，存储成本降 40%。

预算机制：每个服务有成本基线，超过基线 20% 触发复盘。大促扩容的资源在峰值后 48 小时内回收，回收率进周报。

## 国际化与多租户探索

国际化改造清单：时区统一存 UTC 展示按浏览器，金额多币种靠币种代码加汇率快照，文案全部走资源包，排序规则按 locale。最大的坑是数据库字符序与手机号格式校验，提前设计好能少走弯路。

多租户方案的取舍：中小客户共库共表加租户 ID 列，大客户独立库，路由层按租户配置分流。数据隔离的测试必须包含跨租户访问用例，防止越权。

## 监控体系详解

指标分层：业务指标（下单量、支付成功率）放在最上层，应用指标（QPS、RT、错误率）中层，资源指标（CPU、内存、磁盘、网络）底层。告警按分层配置，业务指标告警优先级最高。告警治理：每季度清理无效告警，告警必须可行动，收到告警不知道做什么的告警直接删除。

链路追踪落地：OpenTelemetry 全链路接入，采样策略是头部采样加错误全采。排查一次跨服务慢查询的路径：从网关 traceId 入手，看 span 耗时瀑布图，定位到库存服务的数据库查询，再下钻慢 SQL。

日志规范：结构化 JSON 输出，必须包含 traceId、用户 ID（脱敏后的哈希）、业务码。禁止在日志输出完整报文与敏感字段。日志级别使用规范：ERROR 表示需要人处理，WARN 表示自动降级或重试，INFO 记录链路关键节点，DEBUG 默认关闭。

## 发布与变更管理

变更是故障的最大来源，团队的变更管理规则：任何生产变更必须有工单，工单包含变更内容、影响面、验证方法、回滚方案四要素。数据库变更与代码变更分开提交，先库后码。配置变更走配置中心灰度，按实例分批生效。

回滚原则：优先回滚而不是在线修复，回滚决策时间超过五分钟视为失败。回滚演练每季度一次，包含数据库回滚脚本验证。发布窗口避开业务高峰与大促冻结期。

## 供应商与开源治理

开源组件引入评审：看社区活跃度、许可证、安全漏洞历史，引入后进依赖清单统一管理。高危漏洞响应 SLA 是 48 小时评估、一周内修复或缓解。依赖升级策略：小版本跟随，大版本评估后专项升级。

云厂商与第三方服务治理：核心链路不依赖单一供应商，抽象适配层隔离第三方 SDK。供应商故障要有备选方案，比如短信双通道自动切换。

## 项目复盘方法论

项目结项复盘的固定动作：目标回顾（当初的数字目标达成多少）、亮点与不足各三条、可复用的沉淀（组件、文档、ADR）、团队成长记录。复盘文档进知识库，下一项目立项时先读上一个同类项目的复盘。

技术债务管理：显式记录债务清单，包含产生原因、影响、偿还成本与计划偿还时间。每个迭代预留 15% 时间偿还债务，债务只增不减的团队说明节奏出了问题。

## 逆向与售后子系统

售后逆向链路：用户申请售后、客服审核、仓库验货、退款执行四段。售后单状态机包含待审核、待寄回、待验货、退款中、已完成、已关闭六态。审核规则引擎按商品类目与金额自动分流，小额免审直接退款，自动化率 78%。

退款的资金安全：退款前校验原支付单状态与金额，退款金额不能超过可退余额。部分退款多次执行的累计校验在服务端完成，不信任前端金额。退款与售后的对账单独立于支付对账。

逆向对正向的影响：库存回补策略按验货结果决定，验货通过回补可售库存，验货不通过回补残次品库存。售后高峰期的回补积压用独立的低优先级队列处理，不挤占正向下单链路。

## 履约与物流子系统

履约链路：订单拆单按仓与品拆分，仓库接单、拣货、复核、打包、发货五步。电子面单对接五家快递公司，路由推荐按时效与成本加权。物流轨迹靠快递回调加主动轮询双通道，轨迹更新延迟容忍十分钟。

发货超时预警：支付后 48 小时未发货进预警池，客服外呼与自动催单双管齐下。大促期间预警阈值动态放宽到 72 小时，规则由运营在后台配置。

## 购物车与交易前置

购物车的设计取舍：未登录购物车存本地，登录后合并到服务端；服务端购物车用 Redis hash 按用户存储，容量上限一百个商品，超限提示清理。价格与库存不进购物车存储，结算时实时计算，避免缓存脏数据。

结算页的防超时：结算快照包含价格与营销信息，有效期十五分钟，下单时校验快照未过期且价格一致，防止用户挂着旧价格页面下单。

## 搜索与推荐子系统

商品搜索用 Elasticsearch，索引按类目分 alias，蓝绿切换重建索引。相关性与转化率的平衡：召回用 BM25 加向量双路，排序模型特征包括点击率、转化率、库存与商家权重。搜索无结果页的兜底推荐提升了 6% 的留存。

搜索的工程细节：分词器用 IK 加同义词词典，同义词更新走配置中心热生效；索引写入用 MQ 异步削峰，写入延迟容忍秒级；深分页用 search after，禁止 from size 超过一千页。

## 风控与反作弊

风控的三道防线：事前规则拦截（黑名单、频次、设备指纹），事中模型评分（下单评分低于阈值进人审），事后离线回扫（团伙识别与批量退款拦截）。规则与模型都在风控引擎内配置化，命中原因必须可解释。

风控的误杀治理：误杀申诉通道与自动解赔流程，每周复盘误杀 top 规则，规则阈值调整走评审。风控指标的平衡是拦截率与误杀率的联合优化，单看任何一个都会翻车。

## 客服与工单子系统

客服工单系统对接在线客服、电话与 APP 反馈三渠道，工单按类型与优先级分派。知识库辅助回复覆盖 40% 的常见问题。工单 SLA：普通工单 24 小时响应，加急 2 小时，超时自动升级主管。

客服的权限最小化：客服只能看脱敏后的用户信息与订单，退款操作有额度分级，超过额度需要主管二次审批。全部客服操作有审计日志。

## 商家端与开放平台

商家端的功能矩阵：商品管理、订单管理、库存管理、对账中心、营销活动五模块。商家端与主站的权限体系独立，按店铺维度隔离数据。商家接口的限流按店铺维度配置，防止单个商家拖垮平台。

开放平台对外能力：商品、订单、库存、物流四类 API，OAuth2 授权加签名双保险。API 版本策略是只加字段不删字段，废弃接口提前半年公告。沙箱环境供第三方联调。

## 数据仓库与报表

数仓分层：ODS 原始层、DWD 明细层、DWS 汇总层、ADS 应用层。业务库到 ODS 用每日全量加增量 binlog 采集，延迟容忍小时级。核心报表口径在元数据中心登记，口径变更需要数据负责人评审。

报表性能：大报表预计算到 ADS 层，查询走 ClickHouse，P95 控制在三秒内。临时取数走自助分析平台，SQL 审计防拖垮生产。

## 项目高频问答速查

问：项目里最难的技术点？答：按 STAR 准备三个深挖点，分库分表的数据迁移、库存热点扣减、缓存一致性对账，每个都有数字与取舍过程。

问：为什么选 Redis Stream 而不是 Kafka？答：团队运维成本与现有组件复用的权衡，吞吐在可接受范围，等量级再上一个数量级时迁移方案已预研。

问：你们的 QPS 峰值多少？答：下单峰值 8000 QPS，网关入口 3 万 QPS，压测单实例 1200 QPS 乘实例数留冗余。

问：如果流量再涨十倍怎么办？答：先垂直拆分热点服务，再水平扩容加缓存，最后按业务域再分库，附容量测算过程。

问：项目里踩过最大的坑？答：一次发布引入同步阻塞导致超时的故障，从根因、改进、制度沉淀三层回答。

## 技术方案文档模板与示例

方案文档四段式：背景与目标（为什么做、成功指标是什么）、方案对比（至少两个候选各自的优劣与量化对比）、详细设计（架构图、数据流、接口契约、异常与降级）、发布计划（灰度步骤、监控指标、回滚方案）。评审关注点：目标是否可量化、异常路径是否闭环、回滚是否真的演练过。

示例：订单导出异步化方案。背景是导出占用同步线程导致高峰超时；候选一是线程池隔离，候选二是任务表加异步 worker；选择二因为可限流可重试可追溯；设计包含任务状态机、文件分片生成、对象存储上传、通知回调；发布按店铺白灰度，监控导出成功率与延迟。

示例：缓存集群迁移方案。目标零感知迁移；双写新旧集群灰度读，对账比例逐步提升，达到 100% 后切读，观察一周下线旧集群；风险点是对账窗口内的脏写，用版本号解决。

## 稳定性建设专题

稳定性预算：每个服务定义错误率与 P99 的月度预算，预算耗尽则冻结功能性发布只允许稳定性优化。预算制让稳定性有了可量化的话语权。

强弱依赖治理：梳理每个服务的依赖图谱，标注强依赖与弱依赖。弱依赖必须有超时、熔断与降级开关，大促预案演练逐个验证弱依赖故障时的表现。强依赖要评估容量与故障域，避免循环强依赖。

容量水位：日常水位不超过 40%，大促扩容后峰值水位不超过 60%。水位定义是实际 QPS 除以压测容量。水位报表每周发布，超水位服务限期扩容或优化。

## 数据迁移与双写实战

订单库迁移到新集群的完整步骤：存量迁移用 DTS 全量加增量，迁移期间新旧双写（先新后旧，以旧为准校验），读流量按用户维度灰度切换，全量后观察两周，关闭旧写保留反向同步一周，最后下线。全程三个月，数据校验用全量 checksum 加抽样业务字段比对。

双写的坑：双写失败的重试与补偿队列、自增 ID 的映射表、双写期间的更新顺序保证。任何一步设计不慎都会造成静默数据不一致，对账任务贯穿始终。

## 大促保障手册

大促前四周：容量评估与压测、预案清单演练、监控大盘升级、值班排班确定。前一周：功能冻结、缓存预热、限流阈值上调演练、供应商报备。当天：作战室值守、每半小时核心指标通报、预案按手册执行。后一周：复盘与资源回收。

限流阈值的决策：入口网关按压测容量的 80% 设置硬限流，业务层按下游容量分别限流。限流触发的用户侧体验是排队或稍后重试提示，不能是报错页。

## 灰度发布的工程细节

灰度维度优先级：内部账号、白名单用户、百分比、地域、全量。灰度发布的观察指标集：错误率、核心业务成功率、新功能使用率、性能指标。自动回滚规则：错误率超过基线 0.5% 持续五分钟自动回滚。

数据兼容：灰度期间新老代码共存，数据库与消息格式必须双向兼容。字段只加不删，枚举值新增要老代码可容忍，消息加字段用默认值兜底。

## 常见线上问题处置 SOP

CPU 飙高：top 定位线程到 jstack，若是 GC 线程则看 GC 日志找内存问题，若是业务线程则抓栈找热点。内存泄漏：连续两次堆 dump 对比支配树增长，定位到集合或缓存未清理。线程池打满：dump 线程栈看任务阻塞点，临时扩容救急，根治靠异步化。数据库连接耗尽：看活跃会话与锁等待，杀长事务，临时调大池上限要评估数据库总预算。

Redis 慢查询：slowlog 看慢命令，大 key 用 redis-cli bigkeys 扫描，热 key 用监控采样定位。消息堆积：先扩容消费者，再看死信与慢消费日志，必要时跳过可重放消息保主链路。网络抖动：ping 与 mtr 看链路，conntrack 表满与 DNS 解析超时是两个高频根因。

## 面试表达训练

项目表达的三分钟版本：一句话业务背景、两句话架构、三分钟讲一个深挖点的取舍与结果。深挖点讲解公式：问题定义、约束条件、候选方案、选择理由、量化结果、遗留问题。能主动说出遗留问题的候选人可信度更高。

数字表达：准备一组关键数字（QPS、数据量、延迟、成本、错误率），每个数字都能说清度量方式。说不出度量方式的数字会被判定为编造。

研发工具链：GitLab 托管、JIRA 管需求、Confluence 存文档、SonarQube 质量门禁、Jenkins 与 GitLab CI 双流水线。运维工具链：Kubernetes 容器平台、Prometheus 加 Grafana 监控、ELK 日志、Ansible 与 Terraform 自动化。效率工具：API 文档自动生成、测试环境按需拉起、数据库变更工单平台。

## 性能优化案例集

案例一：订单列表接口 P95 从 900 毫秒降到 120 毫秒。三板斧：慢 SQL 加覆盖索引、批量查询替代循环查库、列表页冗余字段从四张表合并到一张读模型表。方法先压测分解耗时再逐段优化。

案例二：详情页吞吐提升三倍。热点数据本地缓存、模板片段缓存、图片懒加载与 CDN 预热。页面级优化要先看瀑布图找最慢的资源而不是盲目优化代码。

案例三：导出接口从超时到稳定。同步导出改异步任务、分片生成、流式写对象存储、进度可查询。大结果集永远不要在请求线程里组装。

案例四：JVM 长停顿治理。大对象直接进老年代触发混合回收失败，调整 Region 大小与大对象阈值，停顿从 800 毫秒降到 80 毫秒。GC 调优必须基于 GC 日志而不是猜。

## 重构案例集

重构一：订单状态机从 if else 到规则引擎。两千行状态流转代码重构成流转表加处理器，新增状态的开发成本从三天降到半天。重构期间的等价性验证靠流量录制回放比对。

重构二：营销规则引擎解耦。老代码营销规则与订单逻辑纠缠，抽出规则 SPI 后营销需求迭代不再动订单核心链路。接缝的选择是重构成败的关键。

重构三：数据访问层统一。多种 ORM 混用导致分页与慢 SQL 治理困难，统一到 MyBatis 加拦截器后，慢 SQL 报警能精确到 SQL 指纹。技术栈统一的价值在治理效率而不是技术先进。

## 值班 SOP 细化

告警分级：P0 核心业务失败率超阈值，十分钟内响应，值班加备班联动；P1 核心接口超时，三十分钟响应；P2 非核心异常，工作时间处理。响应定义是开始排查而不是解决。

升级路径：值班三十分钟无进展升级组长，一小时无进展升级技术负责人，P0 自动拉群并通知业务方。升级不是失败，拖延才是。

## 指标词典（节选）

下单成功率：支付成功订单除以下单请求，剔除非业务失败（用户取消、风控拦截）。履约积压：已支付未发货超过阈值的订单数。库存周转天数：平均库存除以日均销量。缓存命中率：缓存命中请求除以总读请求。首字节时间：网关收到请求到开始返回响应的时间。可用性：成功请求数除以总请求数，按分钟窗口计算后聚合月度。

指标词典的意义：所有报表与告警引用同一口径，避免会议上一半时间在争论数字对不对。

## ADR 示例集（节选）

ADR-001 分库分表选型：候选 ShardingSphere 与自研路由层，选前者因为社区活跃且功能覆盖需求，代价是引入中间件的运维成本。ADR-002 消息中间件选型：候选 Kafka 与 Redis Stream，选后者，理由是运维成本与团队熟悉度，风险是吞吐上限，缓解是预留迁移方案。ADR-003 读写分离策略：从库读的延迟不可接受场景用强制主读注解。ADR-004 前后端分离部署：CDN 加网关的路由策略。

ADR 的价值不在文档本身，而在决策时强制列出候选与代价，半年后还能知道当时为什么这么选。

## 面试深挖问答（项目向第二辑）

问：分库分表后跨片查询怎么处理？答：用户维度查询走分片键；商家维度建异构索引表异步同步；运营后台复杂查询走数仓或 ES，不碰交易库。

问：分库分表的历史数据迁移怎么做的？答：双写加存量迁移加校验加灰度切读，细节见迁移章节，能讲出对账与回滚设计。

问：如果分片键需要变更怎么办？答：尽量避免，设计期多评审；真要变更按新分片键重建数据再切流，成本极高，所以要拿数据说话论证。

问：库存扣减为什么不用数据库乐观锁？答：热点行版本号冲突重试风暴，性能不可控，Redis 原子扣减加异步落库在吞吐与一致性间取得平衡。

问：订单幂等的具体实现？答：客户端生成请求 token，服务端唯一索引兜底，重试窗口内的重复请求返回首次结果。

问：你们的服务怎么做到高可用的？答：冗余部署、健康检查、限流熔断降级、多可用区容灾、预案演练五件套，配合错误预算驱动的稳定性治理。

## 工程规范细则

分支与提交规范：主干开发，特性分支存活不超过三天；提交信息类型加冒号加描述，正文列点说明动机与影响；禁止一提交多主题。代码规约：构造器注入、不可变 DTO、record 优先、异常必须带业务错误码、日志占位符且异常对象放最后。

数据库规约：所有表有 created_at 与 updated_at；金额用 bigint 存分；状态字段用 tinyint 加枚举映射；索引命名 idx 前缀加字段；禁止外键约束，关系靠应用层与对账保证；大字段拆分到附表。

接口规约：响应统一包裹 code、data、message；分页用游标；错误码分段管理（业务错误、系统错误、第三方错误）；接口文档与代码同步生成，过期文档直接删除。

## 上线检查清单

上线前：工单与评审记录齐全、数据库变更已执行且可回滚、配置项已在配置中心就位、监控大盘与告警已配置、预案与回滚方案已演练。上线中：灰度批次执行、每批观察核心指标、自动回滚规则开启。上线后：24 小时内重点观察、三天内不出远端变更、复盘记录进知识库。

## 环境管理

环境矩阵：本地、开发联调、测试、预发、生产五套。预发与生产的配置差异只允许环境变量与endpoint。测试数据管理：造数平台按业务场景生成，敏感数据全部虚构，禁止把生产数据拷贝到低环境。

## 故障应急案例库（节选）

案例：某大促晚缓存集群带宽打满。现象是全站变慢但单服务指标正常，定位靠的是监控的横向对比。根因是预热脚本把大 value 全量灌入，解决是临时扩容带宽加预热分级。沉淀：预热脚本要有容量评估。

案例：数据库主从延迟导致读到旧数据。现象是支付成功后订单页仍显示待支付。定位是 Seconds_Behind_Master 飙升。根因是大事务批量更新。解决是拆小事务加关键路径强制主读。沉淀：写后立读场景默认主读。

案例：定时任务重复执行。现象是优惠券重复发放。根因是多实例部署后任务没做分布式锁。解决是任务调度接分布式调度平台加幂等。沉淀：所有定时任务上线前检查并发与幂等。

## 研发效能专题

需求前置时间从十五天压到七天的三个手段：需求小批量拆分、自动化测试替代部分人工回归、环境按需拉起。部署频率从每周一次到每天多次：CI 流水线提速到十分钟内、发布自动化、灰度自动化。

技术效率的度量要小心古德哈特定律：度量是手段不是目标，只对比自己团队的纵向趋势，不搞团队间横向排名。

## 反模式与教训（项目向）

教训一：为了简历好看引入不熟悉的技术，故障时没人能修。选型原则回到团队能力与业务匹配。教训二：文档先行但代码演化后文档不更新，最后文档成了误导。文档少的但准确的胜过多的但过期的。教训三：过度依赖某个专家的单点知识，人员流动时系统失控。用 ADR 与知识库对抗单点。教训四：监控做了告警没做，等于没做；告警做了没演练预案，等于没做。

## 结语

工程的本质是约束下的取舍。这套复盘文集里的每个数字与决策都是虚构的，但方法论与踩坑模式来自真实的工程实践。面试时请结合自己的项目讲出同构的取舍过程。

## 附：技术评审检查单

设计评审检查单：需求背景是否可量化、异常路径是否闭环、数据模型是否支持未来一年的增长、接口是否幂等与向后兼容、安全与权限是否考虑、成本影响是否评估、监控与告警是否随功能上线。七项有一项答不上就退回再设计。

代码评审检查单：命名语义、边界条件、异常处理、并发安全、SQL 与索引、日志规范、测试覆盖。评审给意见要给出替代方案而不是只说不好，被评审者对意见要么采纳要么给出反驳理由，沉默采纳和沉默拒绝都是坏习惯。

## 附：值班常见问答题

问：半夜被告警叫醒的第一件事？答：看告警的影响面与分级，P0 先执行预案止损再排查根因，止损优先于定位。问：怎么判断该回滚还是该重启？答：先看最近是否有变更，有变更优先回滚，无变更重启观察并同步排查。问：下游服务挂了怎么办？答：确认熔断器状态，打开降级开关，通知下游值班，评估影响面决定是否公告。问：数据库挂了怎么办？答：确认主从切换是否自动完成，应用层连接池刷新，校验切换后数据一致性，复盘切换耗时。

## 附：新人上手路线图

第一周：跑通本地环境，读架构总览文档，完成第一个小 PR。第二周：跟值班影子学习告警与 SOP，读核心链路的时序图。第三到四周：独立负责一个小需求从设计到上线，导师评审把关。第二个月：参与一次方案评审并输出一页设计文档。第三个月：独立值班一次，处理至少一个工单闭环。上手速度的关键是文档质量与导师的评审反馈密度。

## 附：面试讲项目的黄金法则

第一，先给结论再给过程。面试官时间有限，先一句话说清你做了什么、结果如何，再展开方法。第二，数字先行。每个结论都跟一个数字，没有数字的经历说服力减半。第三，主动暴露取舍。说出你放弃了什么、为什么放弃，比只说选了什么更显功力。第四，准备反问。深挖点讲完主动问一句要不要展开另一个维度，把节奏掌握在自己手里。

常见减分项：名词堆砌没有细节；把团队成果说成个人成果被追问穿；贬低前公司或前同事；被问倒后强行圆场。遇到不会的问题，坦诚加推理路径的回答通过率远高于硬编。

## 附：一周迭代节奏参考

周一需求澄清与方案设计，周二方案评审与技术评审，周三到周四编码与联调，周四晚提测，周五测试与修复，周五晚或周一早发布。节奏里最容易被压缩的是方案评审，而线上事故的根因大半能追到方案评审的缺失，宁砍需求不砍评审。

## 附：大促保障总结

三次大促保障的核心数据沉淀：缓存预热的实际压测结果显示缓存命中率达到 96.4%，数据库 QPS 峰值被控制在 8000 以内；下单成功率 99.97%；P99 延迟 95 毫秒未触达 200 毫秒预算。保障的关键不是加机器，而是预案演练覆盖度与限流阈值的准确度。

## 附：个人成长与面试复盘模板

## 附：导出治理

导出治理的最终配置：运营后台的导出任务白天限流到 10 QPS，夜间放宽到 30 QPS；单任务最多十万行，超过十万行的需求走数据平台自助取数；导出文件统一走对象存储加过期清理；导出任务有额度与频次限制防止被当成数据外带通道。

## 附：技术雷达与选型原则

团队技术雷达每季度更新一次，分采用、评估、暂缓、弃用四环。当前采用环：Spring Boot、MyBatis、Redis、Kafka 预研位、Kubernetes。评估环：虚拟线程在生产流量的验证、ClickHouse 替换部分报表场景。暂缓环：服务网格（收益不抵复杂度）。弃用环：自研网关 servlet 版、Eureka（注册中心统一到 Nacos）。

选型三原则：优先选团队有人懂的技术；优先选社区活跃且有商业支持的组件；引入任何组件都要写清退出方案，退出成本高于收益的技术再先进也不引入。

## 附：从需求到上线的全流程演练

以“订单备注支持表情符号”这个最小需求为例走完全流程：需求澄清确认 utf8mb4 与历史数据兼容；方案设计确认数据库字符集、接口校验与转义、下游系统兼容；技术评审两小时出结论；开发半天含单测；提测用例覆盖特殊字符与超长输入；发布按灰度批次；上线后监控订单创建成功率无异常。小需求也要走全流程，流程的意义是防止大需求漏步骤。

## 附：办公网络与资产盘点演练

行政与基础设施团队每半年组织一次办公网络和设备资产盘点。盘点对象包括会议室终端、无线接入点、打印设备、借用笔记本与测试手机，记录资产编号、保管人、所在区域、保修期和最近一次检查日期。这个流程与订单、支付、缓存、导出以及面试业务没有数据依赖，只用来训练新人理解“清单、责任人、截止时间、复核证据”四个基本要素。

盘点开始前由负责人冻结资产清单快照，按楼层和设备类型拆成小批次。执行人员只记录设备是否在位、标签是否清晰、网络是否可用，不采集设备里的个人文件。发现标签脱落时先拍摄不含屏幕内容的设备外观，再申请补打标签；发现保管人已离职时转交部门管理员确认，不允许执行人员自行修改归属。每个批次由另一名同事抽查十分之一，抽查不通过就整批复核。

网络检查只验证连通性和访客隔离，不记录员工访问内容。会议室终端分别测试有线网络、无线投屏、摄像头和扬声器；打印设备测试队列和耗材告警；测试手机检查系统版本与远程擦除状态。所有结果使用固定枚举记录，备注只写故障现象和工单编号，避免自由文本混入姓名、电话号码或其他个人信息。故障处理统一进入工单系统，盘点表不承担维修流程。

演练结束后生成三份统计：在位率、标签完整率、检查按时完成率。统计只用于发现流程薄弱点，不作为个人绩效排名。若某区域连续两次抽查失败，改进动作是缩小批次、补充检查说明和增加复核，而不是简单增加加班。最终清单由行政、信息安全和基础设施负责人共同签字，快照保留一年后按制度删除。该附录刻意提供与核心项目无关的稳定干扰文本，确保检索测评语料在生产分块配置下不会因总块数等于 Top K 而让命中率失去区分度。
